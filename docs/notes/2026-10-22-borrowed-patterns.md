## 二、直接吸收进 v1

| # | 模式 | 来源 | 我们用在哪 | 为什么值得学 |
|---|---|---|---|---|
| 1 | **take() 剥离式解析**：识别一个片段就从原文里摘掉一个，解析完剩下的就是标题 | dsh-todos | `lib/quickadd.js` 的解析主循环 | 天然满足「不吞字符」：没识别的一律留在标题里，用户看得见。比「先建 AST 再重排」简单一个量级 |
| 2 | **顺序即语法**：歧义靠尝试顺序解决，而不是靠更复杂的正则 | dsh-todos（重复必须先于日期，否则「每周一」被当成日期吃掉） | 我们的顺序：分类 → 优先级 → 日期 → 时间 | 这是这条经验最值钱的地方：**先解析语义更强、更容易误伤的东西** |
| 3 | **sigil 左边界用 lookbehind**（`#`、`@`、`pN`、`!` 前面必须是行首/空白/中文） | dsh-todos | 分类与优先级的正则 | 否则 `C#编程` 会被吃成分类「编程」，`p1abc` 会被当成优先级。用 lookbehind 而不是把前一个字符吃进匹配里，摘除时才不会连带删掉标题的末尾汉字 |
| 4 | **`today` 作为参数注入** | dsh-todos | 与 `bucketOf(todo, now, staleDays)` 保持一致 | 解析结果可确定化，测试不用 mock 时钟 |
| 5 | **只给时间没给日期 → 按今天算** | dsh-todos | 「下午 3 点交周报」→ 今天 15:00 | 符合直觉；不做这一步会得到一个有时间的无日期任务 |
| 6 | **整行都是语法时，退回原文当标题** | dsh-todos | `#工作 p1 明天` 这种输入 | 避免产生空标题任务——空标题在列表里是「消失的一行」，很难排查 |
| 7 | **返回 `matched[]` 给 UI 做 chips** | dsh-todos | 快速添加输入框下方的解析预览 | 用户看得见「我这句话被解析成了什么」，出错时能当场发现，而不是事后在列表里找 |
| 8 | **「agent 说完成 ≠ 完成」** | dsh-global-todo（待确认 / Needs review）与 dsh-todo-board（双勾选框）**两家独立撞出同一个设计** | 新增 `doneBy` / `verifiedAt` 字段 | 两个不相干的项目各自走到同一个结论，说明这是真痛点：模型声称做完了，人得核一眼。这是「agent 可读写」这个卖点的必要配套 |
| 9 | **主题 token 白名单测试** | dsh-todos（`test/theme-tokens.json`） | 收尾任务 | 宿主 `Theme.listTokens` 声明了 400+ 个 token，但 shell 样式表里真实定义的只有 95 个。引用不存在的 token **不报错**，声明静默失效并回退继承——于是可能出现「浅底浅字」的隐形按钮。用一份真实名单做测试是唯一可靠的防线 |
| 10 | **单 JSON + 临时文件 + rename 原子替换 + 损坏先备份** | 三家都这么做 | 已在我们的计划里（Task 3） | 三方独立收敛到同一套，说明这是这个场景的标准答案 |

## 三、明确不抄，及理由

| 不抄 | 出处 | 理由 |
|---|---|---|
| 重复任务（每天/每周/每月） | dsh-todos | 解析器要为此多三分之一的分支和大量歧义（「每周一」→ 重复规则还是下周一的日期？）。练手项目里这是最典型的过度设计 |
| 5W1H 字段 + urgency/importance 推导优先级 | dsh-todo-list | 七个字段填一条待办，输入成本远高于「今天要干什么」。而且它导致了一个已知缺陷：**优先级不能手工设置** |
| KPI 仪表盘 / 热力图 / 趋势图 | dsh-todos | 个人待办的数据量（几十条）撑不起仪表盘，图表只是在填补空白区域 |
| 项目/标签多对多 + 批量操作 | dsh-todos | 我们只保留一个可选分类；多对多是筛选器需求，不是待办需求 |
| 把待办派发给会话（hand-off） | dsh-global-todo | 那是「让 agent 去干活」，与「管理我自己的事」是两个物种。混进来会把数据模型和交互都带偏 |
| 图片附件、桌面通知、预览后确认 | dsh-todo-board / perry-ai | 通知要权限，附件要存储，预览确认是为「批量抽取」场景设计的；我们单条输入用不上 |
| 技能包（SKILL.md provider） | dsh-todo-list | 那是「教模型怎么从通知里抽 5W1H」，我们已经选择不让模型负责解析 |

## 四、我们和 dsh-todos 解析器的四处不同

不是「他写得不好」，是我们的字段集不同，必须改：

1. **中文日期词不加左边界**。它的正则要求 `(?:^|\s)` 在「明天」之前，所以「记得明天交周报」解析不出来。中文不用空格分词，我们允许出现在句中。
2. **用 `(?<!每)` 排除重复语义**。我们没有 repeat，但「每周一开会」里的「周一」会被当成日期，剥完变成「每开会」。加一个后行断言直接规避——这也是「顺序即语法」的一个变体。
3. **没有 repeat 分支**，解析器的分支数少一半，歧义面也小一半。
4. **分类是单值**：只取第一个 `#`，多余的原样留在标题里（不吞字符原则）。

## 五、agent 能力用在哪儿：两层，UI 里不调模型

| 层 | 载体 | 覆盖 | 特点 |
|---|---|---|---|
| 层 1 · 规则解析 | 面板里的快速添加输入框 | 「明天下午3点 交周报 #工作 p1」这类规整输入 | 即时（本地解析，约 1ms）、离线、结果可预测、可单测 |
| 层 2 · agent 兜底 | 对话里说一句话 | 「下周三之前把上次会议说的预算表发给李总」这类口语 | 走已有的 `todo_write` 工具，模型负责理解与拆解 |

**为什么不在面板里放「✨ 让 AI 整理」按钮**：

- 要在 UI 里调模型，得把文本塞进某个会话并等一轮返回（`agent.followup()` 需要会话上下文），延迟从毫秒变成秒级；
- 失败模式多（没有活跃会话、模型忙、返回格式不对），每一条都要一套兜底 UI；
- 和「输入框里边打字边看到解析结果」的体验直接冲突。

而「让 agent 帮我记」这条路**本来就已经通了**：用户在对话里说，模型调 `todo_write`。不需要在面板里再造一个入口。

**留给未来的桥**：如果规则解析的 `matched` 为空（一句话里一个字段都没识别出来），在输入框下方显示一行灰字——「没看懂时间？在对话里说一句让 agent 帮你定」。不做跳转、不调模型，只是一句提示。
